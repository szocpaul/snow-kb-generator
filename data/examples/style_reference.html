Overview / Summary

Content

This interface synchronizes deployment-related Change Requests and Change Tasks between ServiceNow and the Deployment Orchestrator (DO). Communication is routed through the gateway middleware. ServiceNow sends change and task information to DO, while DO returns technical deployment status and transport details.

The integration is used for changes managed through the DO process, including standard and emergency change models. A record is synchronized only when it meets the configured DO identification and trigger conditions.

  • Interface: Bidirectional REST integration between ServiceNow and DO through the gateway middleware.
  • Users: Change Management process users, deployment operators, integration operators, and support teams.
  • Outbound data: Change Request attributes such as coordinator and priority, together with Change Task details such as description, CD state and transport request.
  • Inbound data: Change Task status, CD state, actual start and end dates, and transport information.

Outbound processing starts from ServiceNow Business Rules. IntegrationFrameworkUtil evaluates the trigger configuration, generates the payload and sends the request to the gateway. Inbound updates are received through POST /api/x_snow/do/change/task and processed by ChangeSyncInterface.

Inbound Technical Implementation

Content

The gateway sends Change Task updates to the DO Scripted REST API. The resource delegates processing to ChangeSyncInterface.updateChangeTaskFromAPI(), which validates the request and updates the matching change_task record.

  • Scripted REST service: DO
  • Base path: /api/x_snow/do
  • Resource: Change Task | Post
  • Endpoint: POST /change/task
  • Handler: ChangeSyncInterface.updateChangeTaskFromAPI()

Required parameters

  • number - Change Task number
  • sys_id - Change Task sys_id
  • short_description
  • u_cd_state - CD state
  • u_cd_number - CD number

Payload sample

{
  "number": "CTASK0012345",
  "sys_id": "",
  "short_description": "Deploy transport CD12345",
  "u_cd_state": "Confirmed",
  "u_cd_number": "CD12345",
  "u_cd_transport_request": "TRK900123",
  "u_cd_url": "https://do.example-service.com/...",
  "u_cd_actual_start_date": "2025-08-22 08:00:00",
  "u_cd_actual_end_date": "2025-08-22 10:30:00",
  "cr_u_developer": "developer@example-service.com",
  "cr_u_change_coordinator": "coordinator@example-service.com",
  "cr_u_technical_change_manager": "tcm@example-service.com"
}

Flow and validation

  1. The Scripted REST API authenticates the caller and checks access through the configured internal role.
  2. The handler verifies the mandatory request values. Missing mandatory data results in an HTTP 400 response.
  3. The target Change Task is identified and the supplied CD, transport and date values are applied.
  4. User values such as cr_u_developer are resolved against ServiceNow users by UPN.
  5. If the CD state becomes Confirmed or Withdrawn, follow-up logic may close the task. When all applicable tasks are closed, the parent Change Request can move to Review.

Inbound access is controlled by bearer-token authentication and the related ACL.

Outbound Technical Implementation

Content

Outbound synchronization is triggered by Business Rules on eligible Change Requests and Change Tasks. The implementation uses the shared integration framework for trigger evaluation, payload generation, routing and transaction logging.

Technical components

  • ChangeSyncInterface: deployment-specific validation, payload construction and inbound update logic.
  • IntegrationFrameworkUtil: generic trigger handling, payload generation and REST dispatch.
  • DO Interface Change Request: handles relevant Change Request updates.
  • DO Interface Change Task: handles relevant Change Task updates while the task is in Pending state (-5).
  • DO async CD or ChTask State upd: updates the parent request after a task CD state changes to Confirmed or Withdrawn.
  • REST Message: DO Interface FrameWork, using the gateway production function and https://gateway.example-service.com/${rest_uri}.

Dependencies and authentication

Routing is configured through u_interface_trigger_condition records and their environment-specific REST endpoints. Payload generation can use a referenced u_flow_action; if no Flow Action is configured, the framework falls back to the u_fields mapping.

Outbound requests use mutual TLS configured on the parent REST Message. The required certificate must be installed, valid and bound to the REST Message.

Validation steps

  • Confirm that the Change Request is deployment-managed, including the expected model and correlation_display = 'Deployment'.
  • Confirm that the Change Request has at least one active Change Task.
  • Check that a monitored field has changed and the corresponding Business Rule conditions are satisfied.
  • Updates made by interface.do are excluded to prevent an inbound update from triggering another outbound call.

How to Use the Interface

Content

No manual action is normally required for outbound synchronization. Use an eligible deployment Change Model, such as Standard Change or Emergency Change, and make sure the record meets the configured assignment and trigger criteria.

Outbound

  1. Create or update an eligible Change Request and ensure that it has an active Change Task.
  2. Update a monitored field, for example the change coordinator, priority or a relevant task field.
  3. Open u_interface_transaction and check the latest outbound transaction.
  4. Verify the target endpoint, payload and gateway response.

Inbound

  1. The deployment system or the gateway sends the Change Task payload to /api/x_snow/do/change/task.
  2. ServiceNow validates the request, resolves user references and updates the Change Task.
  3. Check the Change Task for the received CD state, CD number, dates and transport information.
  4. If the final applicable task is closed, verify the resulting state of the parent Change Request.

A successful call is recorded in u_interface_transaction. The transaction record contains the endpoint, request, response and HTTP status used for operational verification.

Testing Guide

Content

Outbound scenarios

  • Update the coordinator or priority of an eligible deployment Change Request.
  • Update a monitored field on a Change Task in Pending state (-5).
  • Verify that the generated payload contains the expected values and is sent to the correct environment.

Inbound scenarios

  • Send a valid request with CD state Confirmed.
  • Send a request with one mandatory value omitted and verify that it is rejected.
  • Send user UPN values and verify that they resolve to the expected ServiceNow users.

Suggested test data

  • Change Request model: Standard Change
  • Assigned user: Dummy Change User
  • Assignment group: Trigger_SNow2DO
  • Linked Change Task state: Pending (-5)

Test procedure

  1. Update u_change_coordinator on the test Change Request.
  2. Check u_interface_transaction for the outbound request and response.
  3. Send a valid JSON request to the inbound endpoint.
  4. Verify that u_cd_state, u_cd_number and the supplied transport data were updated.
  5. Review syslog if the expected transaction or record update is missing.

Known Issues

Content

Outbound synchronization is not triggered

Symptoms: No transaction is created after an apparently valid Change Request or Change Task update.

Likely cause: The record no longer meets the deployment identification criteria, no active Change Task exists, or the updated field is not part of the configured trigger.

Diagnostic steps: Check the model, correlation_display, active tasks, Business Rule conditions and ChangeSyncInterface.isChangeRequestValidToSync().

Resolution: Correct the record or trigger configuration. Legacy records may require verification or migration to the current Change Model.

Prevention: Keep model and trigger configuration aligned across environments and include eligibility checks in regression testing.

Outbound transaction fails

Symptoms: A transaction exists, but the gateway does not accept the request or the connection fails.

Likely cause: Incorrect environment routing, endpoint availability, or an expired or incorrectly bound mutual TLS certificate.

Diagnostic steps: Review the endpoint, payload, response and HTTP status in u_interface_transaction. Check the certificate configuration on the parent REST Message.

Resolution: Correct the endpoint or certificate binding. Engage the Network/Security team for connectivity and mutual TLS problems.

Prevention: Monitor certificate expiry and verify environment-specific routing after deployments or clones.

Inbound update is rejected or fails

Symptoms: The caller receives an error and the Change Task is not updated.

Likely cause: A mandatory field is missing, authentication or role validation fails, or a supplied UPN cannot be mapped.

Diagnostic steps: Review u_interface_transaction and syslog. Compare the request with the mandatory field list and verify user records.

Resolution: Correct the source payload, access configuration or user mapping. Do not bypass request validation in the Scripted REST resource.

Prevention: Validate payloads in the source system and maintain the required integration user access and UPN data.

Investigation Steps

Content

Use this guide when deployment data is out of sync, an expected transaction is missing, or an interface call returns an error.

  1. Identify the direction. Determine whether the failing flow is outbound from ServiceNow or inbound from the deployment system.
  2. Locate the transaction. Search u_interface_transaction using the Change Request or Change Task number and review the latest request, response and HTTP status.
  3. For outbound issues, verify eligibility. Check the Change Model, correlation_display, active tasks, changed fields and Business Rule conditions.
  4. For outbound connection issues, verify routing and mutual TLS. Confirm the selected endpoint, certificate validity and gateway availability.
  5. For inbound issues, verify the request. Check mandatory values, bearer-token access, ACL/role configuration and UPN mappings.
  6. Review application logs. Check syslog for messages associated with do.deployment and for errors raised by the Script Includes.
  7. Reproduce safely. Use a non-production test record and repeat the smallest update that should trigger the interface.
